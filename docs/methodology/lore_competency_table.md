# ФинПульс: Gate 2 / Competency Table для production lore pipeline

**Статус:** gate-документ для human review.

**Дата подготовки:** 2026-07-05.

**Граница approval:** этот документ готовит Gate 2 к проверке. Он не утверждает
Gate 2 от имени человека. Финальное approval и решения перед Gate 3 остаются за
человеком.

## 1. Назначение документа

Competency Table переводит взрослую рамку финансовых компетенций в рабочую
производственную таблицу для будущего лор-курса ФинПульс. Таблица нужна, чтобы
следующие gate-артефакты могли связывать сюжет, эмоцию, финансовую тему и
действие пользователя без возвращения к исходной рамке на каждом шаге.

Документ отвечает на вопросы:

1. Какие компетенции входят в production-relevant subset для лора.
2. Каким наблюдаемым действием пользователя проверяется каждая компетенция.
3. Какие компетенции безопасны для первых двух уровней.
4. Какие компетенции стоит оставить для уровней 4-5.
5. Где есть повышенный safety/fact-check риск или слабая проверяемость.

## 3. Что Gate 2 делает и чего не делает

Gate 2 делает:

- нормализует взрослые компетенции в production-формат;
- задаёт уникальные ID компетенций;
- фиксирует наблюдаемое действие пользователя для каждой компетенции;
- даёт первичные идеи игровых проверок без проектирования уроков;
- отмечает safety, fact-check и overload риски;
- показывает coverage по четырём предметным областям;
- формулирует решения человека перед Gate 3 / Project Bible.

Gate 2 не делает:

- не создаёт Project Bible, Macro Arc, Section Grid, Emotional Model,
  Traceability Matrix, Lesson Cards или Screen Scripts;
- не генерирует 80 уроков;
- не утверждает героя, город, NPC, список эмоций или объекты уровней;
- не меняет runtime JSON, schemas, frontend/backend код, API или persistence;
- не добавляет диагностики, награды, streak, HR-аналитику, B2B-дашборды или
  новые игровые mechanics;
- не превращает компетенции в персональные финансовые рекомендации.

## 4. Правила нормализации компетенций

1. Одна строка таблицы = одна главная компетенция, пригодная для будущего
   назначения уроку или разделу.
2. Каждая компетенция имеет проверяемое действие пользователя: выбрать,
   классифицировать, сравнить, рассчитать, найти риск, проверить источник,
   собрать черновик, упорядочить шаги или распознать манипуляцию.
3. Если исходная компетенция является установкой, в таблице фиксируется
   безопасный proxy: например выбрать поддерживающую формулировку, распознать
   давление или составить нейтральный вопрос. Реальное поведение за пределами
   приложения не объявляется доказанным.
4. Быстро меняющиеся значения не фиксируются как вечные факты. Ставки, лимиты,
   тарифы, вычеты, условия программ и правовые нормы требуют официального
   источника и даты актуальности или формата «найти актуальное значение».
5. Чувствительные темы помечаются отдельно: инвестиции, кредиты, налоги,
   страхование, пенсии, криптоактивы, недвижимость, банкротство,
   предпринимательство и персональные данные.
6. Формулировки остаются образовательными: объяснить механику, риски,
   альтернативы и источники. Нельзя писать «купить», «вложить», «оформить»,
   «продать» как решение за пользователя.
7. Первые уровни должны давать базовые, высокочастотные, безопасно
   проверяемые действия. Продвинутые темы идут позже, когда уже есть язык
   бюджета, риска, источников и договоров.
8. Сюжетный тип ситуации описывается как класс ситуации, а не как сцена.
   Конкретный герой, город, NPC и эмоция появятся только после Gate 3+.

## 5. Поля таблицы

| Поле | Значение |
|---|---|
| ID | Уникальный ID production-компетенции. |
| Предметная область | Одна из четырёх областей взрослой рамки. |
| Взрослая тема | Тема из локального каталога компетенций. |
| Компонент | `знание`, `умение` или `установка`. |
| Уровень сложности | `базовый`, `продвинутый` или `требует осторожной адаптации`. |
| Краткая формулировка компетенции | Операционная формулировка для производства. |
| Поведенческий результат | Что пользователь сможет сделать в интерфейсе или учебном сценарии. |
| Возможная игровая проверка | Тип действия без дизайна урока. |
| Сюжетный тип ситуации | Класс жизненной ситуации, где компетенция может проявиться. |
| Safety/fact-check notes | Ограничения, источники и риски. |

## 13. Риски перегруза пользователя

- Смешать в одном уроке бюджет, кредит, мошенничество и эмоцию: нужно одна
  главная компетенция на урок.
- Дать слишком много юридических или налоговых деталей до навыка «найти
  официальный источник».
- Начать инвестиции до понимания подушки, горизонта цели и риска.
- Превратить установки в псевдодиагностику: «вы тревожный», «вы не умеете
  планировать», «у вас плохие привычки».
- Использовать много чисел без даты и источника, особенно в кредитах, налогах,
  страховании, пенсиях и валюте.
- Делать игровое действие декоративным: пользователь должен решать финансовую
  задачу, а не просто нажимать «продолжить».
- Перегрузить первые уровни продуктами: конкретные банки, брокеры, страховые
  полисы, ИИС, НПФ, налоговые режимы.
- Подменить взрослый тон детскими наградами или внешними баллами.

## 14. Решения человека перед Gate 3 / Project Bible

Перед переходом к Project Bible человеку нужно решить:

1. Утвердить ли этот production-relevant subset как рабочую Gate 2 таблицу или
   расширить его до более подробной версии.
2. Утвердить ID-схему `MNY-*`, `PLN-*`, `RSK-*`, `ENV-*` или заменить её до
   появления Traceability Matrix.
3. Подтвердить mandatory subset для уровней 1-2.
4. Подтвердить список тем, которые откладываются до уровней 4-5.
5. Установить правило для `proxy-check` компетенций: можно ли назначать их как
   главные компетенции урока или только как вторичные.
6. Утвердить source-update protocol для time-sensitive тем: кто и когда
   проверяет ЦБ, ФНС, Госуслуги, СФР, АСВ и условия финансовых организаций.
7. Решить, включать ли high-risk digital offers, crypto/FOREX и банкротство в
   5×4×4 курс или оставить только как safety-red-flags.
8. Решить, должен ли Project Bible учитывать будущий B2B-контур как жёсткое
   privacy-ограничение или оставить его вне lore pipeline.
9. Подтвердить, что Gate 3 создаёт Project Bible, а не Macro Arc, Section Grid
   или Lesson Cards.
10. Подтвердить, что никакая строка таблицы не является персональной
    финансовой, инвестиционной, налоговой или юридической рекомендацией.

## 15. Definition of Done для Gate 2

Gate 2 готов к human review, если:

- документ находится в `docs/methodology/lore_competency_table.md`;
- связанные источники перечислены явно;
- правила нормализации компетенций зафиксированы;
- у каждой строки таблицы есть ID, область, тема, компонент, сложность,
  поведенческий результат, возможная проверка и safety/fact-check notes;
- каждая компетенция имеет проверяемое действие или явно помеченный proxy;
- обязательные компетенции для уровней 1-2 вынесены отдельно;
- компетенции для уровней 4-5 вынесены отдельно;
- high-risk и weak-checkability компетенции помечены;
- coverage audit по четырём областям выполнен;
- риски перегруза и решения человека перед Gate 3 сформулированы;
- документ не создаёт Project Bible, Macro Arc, Section Grid, Emotional Model,
  Traceability Matrix, Lesson Cards, Screen Scripts или 80 уроков.

## 16. Следующий шаг

После human approval Gate 2 следующий шаг - **Gate 3 / Project Bible**.

Правильная последовательность:

```text
Source Pack
        ↓

        ↓

        ↓

```

Неправильный следующий шаг: Macro Arc, Section Grid, Emotional Model,
